3) BLOQUEADORES CRÍTICOS (P0) ANTES DE PUBLICACIÓN OFICIAL
====================================================
3.1 Seguridad de WebSocket (CRÍTICO)
Problema:
- Cualquier cliente puede emitir “join” con cualquier userId y suscribirse a room ajeno.
Impacto:
- Riesgo de fuga de datos/notificaciones entre usuarios.
Qué cambiar:
- Autenticar socket con JWT en handshake.
- Resolver userId desde token en servidor, no desde evento enviado por cliente.
- Rechazar conexiones no autenticadas.

3.2 Fallback inseguro de JWT_SECRET
Problema:
- Se usa process.env.JWT_SECRET || 'your_jwt_secret'.
Impacto:
- Si falta variable, tokens firmados con secreto trivial.
Qué cambiar:
- Fallar arranque si JWT_SECRET no existe.
- Eliminar TODO fallback hardcodeado.

3.3 Endpoints con riesgo de acceso cruzado tenant (multi-tenant bypass)
Problema:
- createService usa salonId enviado por frontend (no derivado del usuario).
- getServiceById no valida pertenencia al salón del usuario.
- createAppointment no valida correctamente ownership de client/service/stylist respecto al salón del usuario autenticado.
Impacto:
- Posible lectura/escritura en datos de otro salón.
Qué cambiar:
- Derivar SIEMPRE salonId del usuario autenticado.
- Validar ownership en todos los CRUD por entidad.

3.4 CORS demasiado permisivo en producción
Problema:
- Se permite cualquier subdominio vercel.app.
Impacto:
- Superficie de ataque innecesaria.
Qué cambiar:
- Lista cerrada de orígenes permitidos por variable de entorno (incluyendo preview si hace falta, pero explícita).

3.5 Ruta de test expuesta en notificaciones
Problema:
- Existe POST /notifications/test en rutas productivas.
Impacto:
- Ruido operativo y potencial abuso.
Qué cambiar:
- Eliminar o proteger estrictamente por NODE_ENV !== production + rol admin interno.

====================================================
4) DEUDA TÉCNICA ALTA (P1)
====================================================
4.1 PrismaClient instanciado en múltiples archivos
Problema:
- new PrismaClient() repetido en muchos controllers/middlewares.
Impacto:
- Riesgo de exceso de conexiones y menor control lifecycle.
Qué cambiar:
- Crear singleton de Prisma en src/utils/prisma.ts y reutilizar en todo el backend.

4.2 Validación de entrada insuficiente
Problema:
- Falta capa homogénea de validación de payloads (register, createAppointment, services, workers, config, etc.).
Impacto:
- Errores de calidad de datos y vectores de abuso.
Qué cambiar:
- Añadir Zod/Joi + middleware de validación por endpoint.

4.3 Inconsistencia de request context
Problema:
- Mezcla de req.user.userId y req.userId según controlador.
Impacto:
- Fragilidad y bugs silenciosos.
Qué cambiar:
- Tipar AuthRequest unificado y usar una sola convención.

4.4 Hardcodes de localhost en backend/frontend
Problema:
- Links en forgot password y marketing usan localhost.
Impacto:
- Flujo roto en producción (emails con links incorrectos).
Qué cambiar:
- Variable pública FRONTEND_URL para construir enlaces absolutos.

4.5 Logging de debug excesivo
Problema:
- Mucho console.log en producción (incluye trazas sensibles de flujo).
Impacto:
- Ruido, coste y posible exposición de datos.
Qué cambiar:
- Logger estructurado con niveles (pino/winston) y masking de datos sensibles.

4.6 Falta middleware de seguridad base
Falta:
- helmet
- rate limiting
- request size limit
- posiblemente compresión
Impacto:
- Menor resiliencia ante abuso y ataques básicos.

====================================================
6) UX/UI Y CALIDAD VISUAL (ANÁLISIS HONESTO)
====================================================
6.1 Inconsistencia fuerte de diseño
Observado:
- Mezcla de estilos Tailwind + CSS custom extenso + gradientes muy distintos por vista.
- Branding inconsistente: “BeautySalon”, “SalonPro”, “Salon Manager”, etc.
- Iconografía mixta (SVG inline, Lucide CDN, clases FontAwesome sin dependencia explícita local).
Impacto:
- Sensación de producto no unificado, menor percepción premium.

6.2 Componentes demasiado grandes
- Hay vistas de 700-1300 líneas (Citas, Resume, Clientes, etc.).
Impacto:
- Muy difícil mantener, testear, iterar diseño, corregir bugs rápido.

6.3 UX técnica mejorable
- Se siguen usando alert/confirm en varias pantallas.
- Muchas vistas duplican lógica de API_URL/token y errores.
- Dependencia total de localStorage + parse directo (riesgo de crash si datos corruptos).

6.4 Accesibilidad mejorable
- user-select:none global en casi toda la UI limita usabilidad.
- Falta revisión a11y formal (foco, contraste, navegación teclado, ARIA).
